# P7 file intake implementation

P7 implements Paychex manifests and the shared local file lifecycle. P8 extends this lifecycle to carrier CSV/webhook events; POD remains P9, and export/SSE remain P11. The approved contracts are FILE_INGESTION.md, INGESTION.md, INTEGRATION_ADAPTERS.md, SHIPMENT_CREATION.md and D50. There is no new HTTP route or frontend screen in this slice.

## Durable state and concurrency

Revision `0004_manifest_intake` adds `ingestion_source`, `ingestion_imports`, `ingestion_rows` and `shipment_field_receipts`, and links existing `ingestion_errors` to sources/imports/logical rows. It inserts no sources, mappings, packages or users. Existing company users/passwords are unchanged.

**Engineering choice:** PostgreSQL is both the durable work queue and checkpoint store for P7. A combined scheduler/worker ticks every second; each source's directory polling interval defaults to 60 seconds and is independently configurable from 1 to 86400 seconds. Pending payload/archive retries are checked independently of the next directory poll. Redis remains disposable support for existing authentication; P7 needs no additional queue dependency.

A PostgreSQL session advisory lock serializes each source across overlapping workers and releases on connection/process death. Different sources can be handled by different workers. A bad source folder/configuration does not prevent the tick from visiting other sources, but still fails that tick and its health heartbeat. The worker revalidates active shipper ownership; CSV fields cannot select a tenant. P7 originally permitted only paychex_manifest; P8 expands the source constraint and trusted CLI to ontrac_csv for active carriers. See CARRIER_INGESTION_IMPLEMENTATION.md.

An arrival is durably claimed by source, original filename and filesystem identity (device/inode/size/mtime). Initial receipt instant and UTC processing date remain stable. Input is then copied into a private processing/import-UUID.csv snapshot, hashed with SHA-256, fsynced and checked for concurrent modification. Only after the checksum is durable is the unchanged original upload unlinked. A crash at any step resumes the same arrival. Producers must finalize immutable files by renaming .part to .csv; replacing or changing finalized input while it is being claimed is unsupported and diagnosed rather than silently deleting changed input.

Content uniqueness is scoped to source/checksum for canonical imports. Identical renamed input waits for an in-progress canonical import and then skips its effects after the canonical import finishes, including partial/failed outcomes. Changed content is a new import. Same bytes under another trusted source remain independent. Skipped duplicates of completed imports archive to done; duplicates of partial/failed imports archive to failed.

## Parsing, receipts and business transactions

Input accepts UTF-8 with an optional BOM, standard quoted CSV fields and newlines. Required headers are Carrier ID, Package ID and Pickup/Destination Name, Address 1, City, State, Zip. Extra columns are ignored. Empty/duplicate/missing headers, invalid encoding/NULs, malformed quoting and file limits are terminal structural failures. Wrong-width logical rows are rejected individually so valid rows survive.

**Engineering limits:** 20,000,000 bytes for parsing, 20,000 data rows and 65,536 characters per CSV field. The restricted raw snapshot is streamed in 1 MiB chunks even for oversized files, preserving all bytes for failed archives; disk capacity/retention must be configured for deployment. Row DTO limits reuse the creation contract; notes are limited to 4000 characters. These are implementation bounds, not throughput claims.

After structural parsing, all logical row checkpoints and global receipt sequence values are committed before business execution. Logical row numbering starts at 2 (header is 1); a quoted multiline field is one logical row. Receipt order represents row acceptance at materialization, before execution, and is retained across retries. Initial file claim alone does not constitute acceptance of unparsed rows. Per-field receipt guards prevent an older accepted row finishing later from replacing a newer valid number, notes or deadline. A newer missing field does not suppress an earlier nonempty correction to that field. Shared creation initializes these guards for API and manifest packages using the Created receipt.

Each row's business effects, checkpoint and counters commit in one transaction. A nested savepoint rolls back invalid row effects while recording a sanitized PostgreSQL reason/source/import/row/reference diagnostic. Completed/rejected rows are skipped on resume. No full CSV row/address/contact content is copied into logs. Raw snapshots/archives remain restricted operator data; the status CLI omits filenames and row contents.

The Paychex transformer preserves string identifiers/ZIP and notes delimiters, trims surrounding whitespace and maps exact documented column names. Carrier ID resolves the trusted shipper's current service assignment. Existing packages retain original assignment, including original-selector authorization after future-only mapping edits; another selector must resolve to that same assignment. Existing updates permit only nonempty shipment number, notes and deadline. D50 preserves service description and order date after creation. Missing values never clear existing values, regenerate numbers/deadlines or add Created events. Addresses and tenant-scoped customer reuse use the shared creation service. Route/third-address/contact/status/price fields do not create additional behavior.

Source dates accept MM/DD/YYYY h:mm:ss AM/PM, MM/DD/YYYY and canonical ISO date/datetime forms. Naive timestamps use the stored recipient validation timezone or UTC fallback; ambiguous/nonexistent local times and malformed values reject the entire row. Order date is the normalized UTC date and is populated only on creation; it is never used as a default-deadline base. Supplied order timestamps still validate on existing-package rows. Default deadline and Created use the import's stable initial UTC receipt time. No source sample is seeded.

## Retry and archive recovery

Payload/capture and archive operations each have at most five attempts, with waits of 5, 30, 120 and 600 seconds before the next attempt. Infrastructure failures retain checkpoints and never assign new row receipts. Business-row errors are final; structural errors do not loop. A database outage cannot durably update its own retry counters, so the process keeps checking database availability without acknowledging unfinished work.

Completed goes to done/YYYY/MM/DD/original.csv; partial goes to failed with completed_with_errors and retained valid effects; structural/unreadable/exhausted input goes to failed. The date is the UTC date captured at initial claim. Archive state is independent of payload state. Target paths are committed before filesystem work. Atomic hard links followed by unlink/fsync prevent overwrite and recover both pre-unlink and post-unlink crashes. Existing target names receive an import-ID suffix (and an additional random suffix if necessary). Storage must support hard links and keep upload/processing/archive on the same filesystem.

After capture retries exhaust, an unreadable regular input can be linked into failed without reading its bytes; a partial capture is discarded only after verifying the complete original is still present. Its checksum remains NULL rather than inventing a digest. If the original has been externally removed/changed or storage remains unavailable, archive retries exhaust with a durable diagnostic and retained available input for operator repair. This is not reported as a successful archive.

After repairing storage, `retry-archive --import-id UUID` resets only exhausted archive attempts; it never replays package changes. Failed payloads/business rows are not polled for automatic replay. Corrected, changed input can be finalized as a new import; manual payload replay is not a required UI.

## Local operation and verification

Follow DEVELOPMENT.md for explicit migration, bind-mount ownership, optional ingestion profile and trusted source registration. No real SFTP daemon, remote credentials, AWS account or sample account mapping is installed. `status` shows the last 100 imports and their counters/reason/archive state. Worker health requires a successful database/source tick within 120 seconds; it does not certify every import succeeded. Inspect import/archive outcomes separately.

Run `sh scripts/verify-p7.sh` for all disposable PostgreSQL/Redis tests plus standard backend/frontend/build/HTTP checks. Tests exercise final rename, duplicate/changed content, concurrent/source-isolated claims, partial files, invalid structure, immutable creation metadata, receipt ordering, crash recovery, archive collisions, bounded retries, full raw-byte preservation, timezone validation and prior-slice regressions. Actual executed counts and local deployment results are recorded in tasks/plan.md. Full real-backend browser E2E and production performance/retention sizing remain P12/deployment work.
