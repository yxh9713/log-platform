# Security and Authorization

## Shipper sessions
Authenticate email/password/company slug and verify active company membership. MVP dashboard requires company_type=2. Store password hashes, reject invalid credentials without leaking account existence, validate token expiry/signature and rate-limit authentication.

**Implemented engineering choices (P3):** Shared Argon2id password hashing plus signed, PostgreSQL-backed eight-hour sessions, HttpOnly same-origin cookies/bearer tokens, logout revocation and Redis login throttling. See [AUTHENTICATION.md](AUTHENTICATION.md) for the complete lifecycle and guards. Token transport must support authenticated API and SSE consistently. Do not put bearer tokens in public URLs. No MFA/refresh/account-recovery UI is added without scope approval.

## Tenant and role checks
Scope shipment queries/mutations/joins by verified shipper_company_id. Validate customer, area, detail, import-error, export-job and artifact access in the same tenant. Administrator role permits manual area CRUD/restore within the company, not cross-company access. Ignore client attempts to choose company scope/role.

## Carrier API keys
POST /v1/webhook/{integrationId} uses raw integration ID for routing. X-API-Key carries the raw secret; integrations.apikey stores only its verifier. Verify against that routed integration, then authorize carrier/account/shipper_ref assignment. sign is POD name only.

Administrator manually provisions/shares the raw key and inserts its hash. **Engineering choice:** SHA-256 hex verifier for a high-entropy random key, constant-time digest comparison. UUIDv4 from a secure generator is acceptable; a 32-random-byte URL-safe token is recommended. No key-management UI is required.

Manual verifier replacement revokes the old key immediately; cached credential state must not keep it valid. Missing/incorrect/cross-integration key returns HTTP 401 before ingestion:
```json
{"message":"Invalid API key"}
```

Integration keys are not generated by development company/user seeding. Development user password generation is separately authorized in SEED_DATA.md.

## Untrusted input and storage
Bound CSV/image/request sizes and resource use. Validate source paths against trusted roots; prevent path traversal and cross-source claims. Escape CSV output and handle spreadsheet formula hazards without mutating stored truth. Validate JPEG/PNG and decoded size before resize/storage.

Logs contain correlation/outcome metadata, not credentials, full base64 or unnecessary addresses/phone data. Restrict archived inputs/prepared image content and PostgreSQL error access to authorized processing/users.

## Exports and notifications
Authorize the requesting shipper and retain requester/company scope in durable export jobs. Authenticated SSE subscriptions and download/job retrieval must enforce that scope. Redis live messages do not substitute for durable authorization or readiness.

Public S3 URLs for future POD/exports are a stated product target. Do not silently replace them with a different access model; production bucket, retention and release controls are later configuration work. Local dummy URLs must not be claimed as successful external uploads.

## Verification
Test overlapping identifiers/accounts across companies, wrong integration keys, role escalation attempts, read/write/join/artifact isolation, disabled memberships, source path abuse, input limits, exact authentication errors, key replacement and seed password hashing/idempotency.
